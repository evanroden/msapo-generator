## Hard invariants and abort policy

1. **Exactly one authority for writes.** A durable, independently verified write fence (covering UI, background tasks, direct old-host URL, uploads, artifacts, SQLite/DB and Smartsheet claims) prevents Render/Azure dual writers. A DNS switch or browser banner alone is *not* a fence. Confirm effective active writable instances **1 or 0**, never 2; no overlapping write-capable slots/revisions/restarts.
2. **No acknowledged work lost.** At each handoff, capture a verified snapshot and an immutable post-cutover change journal/export; do not roll back live data without reconciling all Azure-acknowledged saves and external attempts. If reconciliation is impossible, remain in maintenance, not split-brain.
3. **Deploy exactly what was tested.** Final SHA, image digest, renderer/font inventory, `APP_GIT_COMMIT`, `PUBLIC_SITE_ORIGIN`, schema/application migration range and recorded build provenance match in staging and production. No `latest` rebuild, branch drift or automatically deploying from both GitHub repos.
4. **Entra authentication is not report authorization.** Only permitted users/roles may access records of a given contract/site and originals/exports. Do not bind legacy anonymous cookie/browser preferences to the first new Entra user. Unassigned/wrong-tenant/unauthorized paths, including direct download and WebSockets, fail closed.
5. **External submissions are independently fenced.** Keep Smartsheet direct API mode disabled unless separately authorized. Preserve idempotency keys and uncertain/partial outcomes; a retry or rollback must not create a duplicate row. Never treat a timeout as proof no external side effect occurred.
6. **Zero tolerance for release blockers:** any failing required check, unknown schema compatibility, mismatched source/file hash or missing export scope, unauthorized access, broken save/reopen, incorrect output, duplicate submission or unbounded data loss = **NO-GO**. Runtime process health and `/_stcore/health` alone do not establish safe save/generate readiness.

## Rollback decision tree — independent code and data choices

**Immediately:** A12 declares hold; enforce a global write fence on **both** origins, stop external submits and new schema changes, capture Azure's current logical export/changes/snapshot, watermarks, open claims and hashes. Record incident epoch and recipient acknowledgements. Never roll back based only on a failed health check; identify data/schema state first.

| Fault/state | Allowed recovery | Hard guard / proof |
|---|---|---|
| App image regression, persisted data/schema still compatible | **Application-only rollback** to last accepted `D-1` on **the same authoritative Azure data**, or forward fix. Restore just the application image/config; re-run app smoke and save/reopen. | Both `D-1` and current schema compatibility established **before** deploying. Slot swap is not DB rollback and can start another writer; fence nonactive slot. Do not restore an older DB snapshot for an app-only fault. |
| Irreversible or backward-incompatible schema applied | Prefer **roll-forward** compatible repaired image/migration, with Azure fenced. If unavailable, plan an explicitly approved data restore and deterministic replay onto a tested compatible target. | Never start `D-1` against an incompatible new schema. Check migration version, expand/contract policy, and every report/object version before starting. |
| Data corruption/storage loss **before any Azure accepted writes** | Restore verified frozen source snapshot into isolated Azure target, validate, then recommission Azure. Render remains fenced until explicit return decision. | Zero Azure postcutover commits must be independently proved; full counts/hashes/schema and backup restoration verified. |
| Corruption **after any Azure accepted writes** | Recover latest valid Azure point and **replay/reconcile every acknowledged Azure write** from a durable log/backup, preserving versions, original hashes, approvals, object IDs and external submission claim keys. Prefer forward recovery. | RPO of zero *acknowledged* writes is a cutover acceptance requirement; if all writes cannot be reconciled, **hold maintenance and business escalation**, never silently drop them. Snapshot restore by itself is insufficient. |
| Consider returning traffic to Render | Only after verified **reverse synchronization** of Azure-only changes to a schema-compatible Render target, full consistency checks, external claim reconciliation and a controlled Azure-off / Render-on writer lease handoff. | The frozen original Render database is not current after Azure writes. DNS rollback alone would lose work and create split brain. Any proposed reverse import must be dry-run-tested before a real cutover. |
| Unknown Smartsheet/AI external outcome | Keep submit action locked; look up the remote record/state using immutable business key and log outcome before any retry. | Never infer noncreation from timeout. Restore idempotency/claim store together with report state and external reconciliation. |

The **data restore point and replay protocol** must be tested with the chosen Azure stores. Define ENFRA-approved RTO/RPO and acceptance-window duration in the restricted change record; no values are approved in this source. Rollback rehearsal evidence is in `ROLLBACK_REHEARSAL_RESULTS.md`. The **operator** must distinguish image failure, data failure, identity failure, external integration uncertainty and DNS-only problem. Stop conditions always trump an elapsed cutover window; there is no automatic 'go back to Render' switch.
