## 2. As-is Azure Container Apps inventory: read-only proof requirements

An environment/registry/identity/storage *name* shared by prod and dev is a **potential shared failure/security/data boundary**, NOT proof they share the same file bytes or access scope. Storage paths, NFS export/share, subdirectory boundaries, mount options, RW/RO access and real file ownership must be checked together. Likewise, a declared Log Analytics resource is not proof that the applications send console/system/ingress logs to it; App Insights and staging were **not observed**, not proved absent.

Record each field per app/revision in a restricted evidence table: UTC time, read-only operator role, app/environment, revision, exact effective config, evidence artifact reference, observed response, and reviewer. **Do not paste raw exports into this public repository or public CI.**

| ID | Inspect in authorized read-only session | STOP / next smallest safe action |
| --- | --- | --- |
| ACA-01 | App revision mode (Single/Multiple), list **active** revisions, latest/ready revision, actual traffic weights, direct revision/label endpoints, min/max replicas and scale triggers. | If multiple possible writers or unknown, no data-changing tests; inventory revision and ingress routing first. |
| ACA-02 | Current image **reference AND registry-resolved immutable SHA256 digest per active revision**; declared APP_GIT_COMMIT vs actual served About identity; provenance to repository source and renderer/font versions. | A tag such as v1 is not an immutable digest. Resolve via authorized registry read; do not infer image contents from tag. |

Suggested read-only operator procedure (run ONLY in approved, restricted shell; variables set there; retain raw output privately, publish only PASS/BLOCKED summaries):

## 3. Selected destination and architecture decision

**Current migration plan:** App Service Linux custom container as documented in [MIGRATION_MANIFEST.md](MIGRATION_MANIFEST.md); **existing ACA remains an as-is system requiring independent inventory**. No automatic repurposing of either ACA app; no assumption that it is staging. Before detailed execution, the change authority must sign one restricted statement identifying (a) authoritative **current** production writer, (b) approved **future** destination, and (c) whether existing ACA is to be kept, isolated, retired or considered a separately authorized alternate. This is a **decision gate**, not a request to provision.

If **App Service remains the selected future destination**:
- Follow #857's App Service-specific prerequisites and #859's unprovisioned IaC, not ACA revision operations.
- One-worker Linux custom container on port 8501, exact source commit + pinned digest; verify stream WebSocket, protected authentication/group/site role, file and transactional data semantics before acceptance.
- Deployment slots, if they are ever approved, must have independent write-disabled data paths until single-writer fencing is demonstrated. Slot swap is not data rollback. No slot existence/configuration is currently proved.
- Mounted Azure Storage and SQLite are **not** treated as production safe by declaration; managed DB/object adapters in #851 are unactivated. Confirm alternative approved transactional path or actual assessed mount contract, backups and restart/concurrency tests.

If **ACA is separately selected for future production**:
- Do not use App Service WEBSITES_PORT, Easy Auth or slot semantics. Use actual revision settings and ACA authentication/ingress model.
- In **Single** mode the platform shifts to the ready new revision; do **not** assume zero writer overlap during provisioning. In **Multiple** mode only observed traffic weights/activated revisions can support traffic-splitting claims; labels and direct revision access must also be fenced.
- With current single-writer SQLite/file assumptions, do not send production traffic to two active writable revisions, regardless of percentages. An **image-only** revision rollback is permissible only when stores/schema remain compatible and exactly one writer owns state. An image rollback never reverses database changes.
- No ACA traffic change, revision rollback, mode change or update is authorized by this document.

## 5. Observability, readiness and operational response

**As-is ACA:** Only after confirming the ACA environment's logs destination and actual ingestion, use its **console and system logs** and, when configured, **ingress HTTP logs**. In Log Analytics, verify actual table existence/schema and ingest times before using ContainerAppConsoleLogs_CL, ContainerAppSystemLogs_CL or HTTP log tables. The owner inventory's workspace does **not** establish live collection. No App Insights is evidenced. A11 [#856](https://github.com/evanroden/msapo-generator/pull/856) contains **disabled App Service-oriented** alert/KQL templates: they must be adapted/qualified against actual ACA tables before any ACA use, rather than copied and presumed live.

**To-be App Service:** Follow #856's proposed app/host readiness and declared monitoring model only **after** target creation and observed diagnostic settings; no assumed App Insights, staging instance, AppEvents table or action group. Alert receiver, threshold and cost require approval before enabling. Never route raw converter stdout/stderr, HTTP query strings, token-containing URLs, uploaded document text, prompts, identities or report content into central logs.

Readiness MUST be stronger than container process liveness. Define safe synthetic probes with real auth/WS + scoped read/write/reopen in isolated stores, storage/object access, transaction locks, renderer availability and external-submission fail-closed state. A normal 200 from /_stcore/health is liveness, **not** proof users can save.

| Safe signal | Trigger/reaction | Accountable role (not yet assigned) |
| --- | --- | --- |
| Revision image/startup/probe unhealthy, 5xx, ingress/WS failure | HOLD rollout, compare expected digest/probe, inspect sanitized platform logs | Azure platform + app on-call |
| Auth/tenant/role/site scope failure or direct-original leak | DENY access and fence affected route; preserve redacted evidence | IAM/security |
| Save failure, stale version/lock conflicts or storage unavailable | HOLD new writes, preserve original/draft, check claims and cross-store consistency | DBA/storage + app |

| Smartsheet uncertain result/retry | Block duplicate; reconcile sandbox remote claim before retry | PO/integration owner |
| Last good backup absent, mismatch or unproven restore | NO-GO until matched all-store isolated restore passes | Backup/data custodian |
| Missing telemetry heartbeat OR ingestion gap | Independent outside-process absence check and native health correlation | SRE/on-call |

**Operational ownership/targets are decisions, not inferred facts:** name primary + deputy for service/SRE, DBA/backup, IAM/security, P20 code release, integration, business/data and change commander; incident acknowledgement/escalation, coverage window, retention, log cost, RTO and RPO. #856 suggests **RTO <=4 h / RPO <=1 h** only as an *unapproved candidate*, not an SLA. Require isolated restore timing, last durable consistency point and largest measured acknowledged-write gap to demonstrate whichever objectives are signed. RPO measures potential acknowledged work loss, not just backup frequency.

## 7. Rollback branches and known data-loss window

- **Application-only regression, store/schema compatible:** While keeping *exactly one* writer and the same authoritative target data, restore previously accepted **digest D-1** using *that platform's* deployment/revision mechanism. Prove save/reopen/output again. Do **not** restore an older DB merely to roll back an image.
- **Storage/corruption or incompatible schema:** Stop writes to every host, preserve incident state, choose the last validated **cross-store** consistency point, restore to isolated approved target, replay/reconcile **all acknowledged writes and external submission claims** after the checkpoint before opening one writer. If any receipt/claim cannot be reconciled, maintain maintenance/HOLD; no assumed automatic loss-free rollback.
- **Return to old host:** Only if a privately rehearsed reverse migration, compatible schema, delta/claim replay, saved history, full writer fencing and business signoff exist. An old DNS route or ACA revision activation alone cannot restore newer Azure data. Otherwise **forward recovery** with the new data authority, not a blind host revert.
- **Data-loss accounting:** record T0 source-fence time, last consistency-point timestamp B, T1 first target writer enable, T2 last acknowledged target save, and T3 rollback/fence. List every acknowledged save/external action in (B,T3], prove replay, and calculate maximum *unrecovered acknowledged work* and elapsed outage. The current real **RPO/RTO are UNKNOWN**, rollback window is **UNAPPROVED**, and zero-loss reconciliation is **UNPROVED**. Never claim zero loss from a clean restart or eight simulated model checks.
